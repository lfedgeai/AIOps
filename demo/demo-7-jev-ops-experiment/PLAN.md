# Implementation Plan

Status: **implemented** (v0.1.0, 2026-10-19). This file is the original implementation prompt for the project, kept as written. The project built everything below as Tier 1 and ran it against real Jev ([docs/results-2026-10-18-tier1-jev.md](docs/results-2026-10-18-tier1-jev.md)). Tiers 2 to 4 go beyond this plan. They are specified in `openspec/specs/`, with each change's proposal, design and tasks in `openspec/changes/archive/`. The limits below (no Kubernetes, Prometheus, Grafana or Docker Compose) applied to this first version, which is now Tier 1. They still apply to Tier 1. They do not apply to the later tiers.

Use this as the implementation prompt. It keeps the first version deliberately small and leaves room to evolve it later.

Create a small GitHub project that experimentally tests whether Jev AI can make operational decisions from server-state information.

## Objective

Build a reproducible first-version experiment:

**synthetic server statistics → Jev AI → operational decision → comparison against expected outcome**

Do not build a production monitoring system. Do not introduce Kubernetes, Prometheus, Grafana, or other infrastructure yet. The purpose of this version is to validate the core decision-making experiment.

## Requirements

### 1. Generate synthetic server state

Create a deterministic/randomized generator that produces realistic server observations including:

* CPU utilization %
* memory utilization %
* disk utilization %
* system load
* network errors
* application error rate
* API latency
* service statuses
* recent events/restarts

Do not generate completely independent random numbers. Define realistic scenarios where the statistics correlate with the scenario.

Initial scenarios should include at least:

* `healthy`
* `degraded`
* `critical`
* `ambiguous`
* `contradictory`

Each generated scenario must have an independently defined expected operational outcome. The expected outcome must NOT be generated by Jev.

Allow a random seed to be specified so an exact experiment can be reproduced.

### 2. Define operational decisions

Jev should be asked to make bounded decisions rather than generate free-form recommendations.

At minimum evaluate:

**Severity**

* normal
* degraded
* high
* critical

**Recommended action**

* observe
* investigate
* restart
* escalate

**Human review required**

* yes
* no

The exact Jev API integration should follow the current Jev API documentation. Do not invent API parameters. Make the Jev integration isolated behind a small adapter/module so it can be changed without restructuring the experiment.

### 3. Run the experiment

Provide a simple command such as:

```bash
python run.py
```

Allow options such as:

```bash
python run.py --scenario degraded
python run.py --scenario random
python run.py --scenario ambiguous --seed 1234
python run.py --runs 100
```

The output for an individual run should clearly show:

1. Scenario
2. Generated server observations
3. Expected outcome
4. Jev decision
5. Jev confidence/probability, where available
6. Whether the decision matched the expected outcome

Example:

```text
Scenario: degraded
Seed: 1234

Server state
------------
CPU:          78%
Memory:       81%
Disk:         74%
Load:         5.2
Errors:       31/min
Latency:      842ms
Worker:       degraded

Expected
--------
Severity:     high
Action:       investigate
Human review: no

Jev
---
Severity:     high
Action:       investigate
Human review:  no

Result: PASS
```

### 4. Batch evaluation

Support running many scenarios automatically.

For example:

```bash
python run.py --runs 100
```

Produce a summary containing:

* total tests
* correct decisions
* incorrect decisions
* accuracy by decision type
* accuracy by scenario
* average Jev confidence
* confidence for correct decisions
* confidence for incorrect decisions
* latency if available

Also write machine-readable results to JSON/JSONL so results can be analysed later.

Example:

```text
Overall
-------
Runs:          100
Correct:        87
Incorrect:      13

By scenario
-----------
healthy         20/20
degraded        18/20
critical        19/20
ambiguous       16/20
contradictory   14/20
```

Do not hard-code or fabricate these results; calculate them from the actual experiment.

### 5. Important experimental principle

The expected outcome is the ground truth for the synthetic scenario and must be defined independently from Jev.

Do not construct the expected answer by asking another LLM.

The experiment should therefore test:

```text
Known scenario
      ↓
Known server state
      ↓
Jev
      ↓
Decision
      ↓
Compare against independent expected outcome
```

Pay particular attention to ambiguous and contradictory states. We want to see whether Jev behaves sensibly when the evidence does not cleanly point to one action.

### 6. Project structure

Keep the project simple and modular. A reasonable starting structure is:

```text
jev-ops-experiment/
├── README.md
├── requirements.txt
├── .env.example
├── run.py
├── generator/
│   ├── __init__.py
│   └── server_state.py
├── scenarios/
│   ├── __init__.py
│   └── definitions.py
├── jev/
│   ├── __init__.py
│   └── client.py
├── evaluation/
│   ├── __init__.py
│   └── evaluator.py
├── results/
│   └── .gitkeep
└── tests/
```

You may adjust the structure if there is a materially better design, but avoid unnecessary abstraction.

### 7. Reproducibility

Document:

* prerequisites
* Python version
* installation
* Jev API configuration
* environment variables
* how to run one scenario
* how to run a batch
* how to reproduce a run using a seed
* how results are stored

Use `.env.example` but never commit API keys.

### 8. Testing

Include unit tests for:

* scenario generation
* deterministic seed behaviour
* expected outcome definitions
* evaluation/comparison logic
* result aggregation

Do not write tests that simply assert that Jev produces a particular answer. Jev's output is what we are measuring.

### 9. Docker

For this first version, Docker is optional rather than the primary execution mechanism.

If straightforward, provide a minimal Dockerfile so another person can reproduce the experiment without installing Python dependencies manually. Do not introduce Docker Compose or Kubernetes unless actually required.

The architecture should, however, make it easy to containerize later.

### 10. README

The README should explain the experiment in plain language:

> This project tests whether Jev AI can make bounded operational decisions from synthetic server-state information. Server conditions are generated from predefined scenarios with independently defined expected outcomes. Jev receives the observations and selects from a bounded set of operational decisions. The experiment then compares Jev's decisions against the expected outcomes and records accuracy and confidence.

Clearly state that this is an experimental benchmark, not a production autonomous remediation system.

## Implementation approach

Before writing code, inspect the current Jev API/documentation and determine the correct API usage. Do not guess the SDK or request format.

Then implement the smallest working end-to-end path:

1. Generate one scenario.
2. Send it to Jev.
3. Receive the decision.
4. Display the decision.
5. Compare it with the expected outcome.

After that works, add the scenario set, batch execution, evaluation, persistence, tests, and optional Docker support.

Keep the implementation simple. The primary goal is to establish a credible, reproducible experiment rather than build a generalized AI Ops platform.
