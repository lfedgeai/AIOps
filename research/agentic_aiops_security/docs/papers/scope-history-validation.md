*O'Neill Joseph. Working paper, November 2026. Companion to "Where the Scope-and-History Argument Does Not Follow." The question is whether the conclusions follow from the architecture. Empirical tests are left for later.*

## Abstract

Scope & History-Aware Agentic Security is a wrapper around SPIFFE/SPIRE. SPIRE already answers which workload is calling and which node it runs on. The wrapper is for the attacks that succeed with that answer intact, because the context changed. This paper reconstructs that claim for four classes: a direct prompt injection, an indirect prompt injection carried back across a trust boundary, context hacking of the shared brief, and a temporal attack that reuses authority or memory after its time has ended.

The argument has six steps. A published check value binds the system prompt, so a direct injection cannot replace the formulation. The orchestrator's plan is revised against a policy-as-code engine until it passes or the revision limit is reached, and the dispatcher mints along security boundaries, so one agent is not given the core and the internet in a single profile. A cold-start agent's first task is fingerprinted in the sandbox. The drift result the Recorder already computed is forwarded to the workload host, and that run becomes the reputation base run when the result stayed inside organizational policy and guidance and adhered to the system prompt. Behavior outside that baseline is confined to the sandbox and cannot be exfiltrated. A Recorder admits a finished report to workload memory only after drift, sanitization, a direct-injection check, and a chain audit, and discovery reports live in a separate memory. A chain the audit calls dangerous is stopped and quarantined, and it is not a brief. The redo is a bonded agent: read-only, one-shot, and published only to the nodes that produced the failed report. A bonded report that shows the same fault is kept for forensics and is never added to memory. The admitted report is the only context a repeated task receives, because the agent's context, tool calling, tool cache, memory, and indices are cleared. The Bellman list is the clock. A revocation forces a publication, unused agents carry a countdown, and SPIRE issues a token only when that countdown outlasts the token and a resetting publication comes first.

Under those steps, an instruction fetched from a vendor site or the open internet does not become the next task's brief or the planning context. A quarantined chain is not added to memory, and a bonded report that shows the same fault is kept for forensics. Whether that instruction's writes reach the primary store is the assumption that is still open. The steps are valid only with the assumptions in Section 4. The ones the note now states are the wrapper's place on SPIFFE/SPIRE, discovery in its own memory, the bounded policy revision of the plan, fingerprinting as the first task, the exclusion of the best-guess addendum from the system prompt, and the quarantine of a dangerous report chain, with a bonded read-only redo whose failed report never enters memory. The one it still leaves open is whether an indirect injection's shards are reconciled on the profile alone.

## 1. The conclusion

A senior leader asks a local assistant for a report that joins an internal product with its supply chain. The work has to cross four trust boundaries: the core network, the intranet, a vendor's federated network, and the open internet. Trust, governance, and traceability fall at each step outward. At the far end the agent retrieves a page that contains an instruction. A valid SPIFFE identity will carry that instruction home. If the instruction is written into the swarm's shared context, or into the graph the next task will read, the injection has crossed from none-trust into the core by living off the agent's own access.

The same pattern appears in smaller form inside one boundary. Two database tools share a credential. One deletes malformed sensor rows as they arrive. The other deletes old drafts in bulk. An infrastructure agent that speaks for an administrator must still be unable to read a remote HR repository or ask about a firewall. A person, and an agent, can also return from outside the organization's boundary with context that does not belong on the home network, such as a configuration copied from an open forum.

The wrapper's claim is that these are context attacks, and that SPIFFE/SPIRE does not see them. A direct prompt injection tries to replace the task in the request itself. An indirect prompt injection rides in data retrieved across a boundary. Context hacking writes that instruction into the brief, the graph, or the next task. A temporal attack reuses a context or a commission after its time: a finished task's memory, a token issued past an unused agent's countdown, or a reputation entry older than its window. The formulation is fixed and published, local history defines expected behavior, and work that fails those checks cannot enter the primary store, the workload memory, or the discovery memory. The agent can do the assigned task. The instruction it picked up cannot become the next task.

This paper asks whether that claim follows. It does not ask whether a guardrail model is accurate, or how often a monitor fires. Those are later questions. A theoretical architecture is sound when each conclusion is entailed by premises the architecture actually supplies.

## 2. Premises the architecture supplies

The note wraps SPIFFE/SPIRE. SPIRE already answers which workload is calling and which node it runs on, and it can do so from a local cache [@spiffe; @spire]. The wrapper adds the formulation, the local history, and the time window. It leaves identity and node attestation where they are.

**Discovery.** Before planning, the dispatcher mints a short-lived agent with one hardcoded task: poll the resources the current role can already see, read-only, and return what is available. A new role, a node that has been absent, or a node that has appeared starts another cycle. The Recorder files those reports in a memory the workloads do not share. The orchestrator and the dispatcher plan from that memory. A prompt injection in a workload's context has no write into the picture of the network.

**Minting.** An agent is created with a fixed system prompt. The prompt, together with creation metadata, produces a public check value. The Bellman broadcast, signed, publishes which agents are valid, which are being commissioned, and which are being decommissioned, and it carries that check value. A revocation is volatile, so it forces a Bellman publication rather than waiting for the next scheduled one. The same list carries a countdown for each unused agent, so every node can see which agents are near decommission. A later publication that still includes an agent resets that agent's countdown. At the resource, the gateway hashes the system prompt it is presented with and compares the result to the check value in its local registry. A prompt that does not match is not the minted agent. Every cold-start agent is sent to the sandbox for its first task, and that task is the fingerprint. The dispatcher adds a best-guess workflow addendum to that agent's first user prompt, and not to the system prompt. The addendum is drawn from previous similar workloads or from a synthesis of several workloads. Some minted agents carry a sandbox dry-run flag. They simulate the workload and return a safe or unsafe report from the gateway. That flag is not the rule for every agent.

**Bonded agents.** A bonded agent exists for one occasion: a Completed Work Order Report has failed. It is not a second kind of ordinary workload. The whole prompt, including the delegated prompt, is hashed, and that check value is published before the agent is dispatched. The publication is synchronous, and it goes only to the nodes that did the work behind the failed report. Several bonded agents may be used. Each does one part of the task, and each returns only to the Recorder. The gateway treats a bonded agent as read-only. The agent is used once. It disappears when its report is submitted, and a further Bellman update removes it from the list. The Recorder checks that report for the same fault that failed the minted agent. If the fault is isolated, the Recorder annotates it and tells the orchestrator and the dispatcher to avoid or work around that source. The report is kept for forensics and is never added to memory. If the workflow cannot continue without it, the workflow fails, the findings are reported to the user, and the failure is logged. Identifying, assessing, and blacklisting the resource that caused the fault is outside this architecture. The architecture avoids the source.

**The gateway's questions.** SPIFFE/SPIRE answers whether this is an approved agent and where it came from. The Bellman countdown answers when the work is supposed to be done. The profile answers what it may do and request from this resource. A transaction token answers whom it is working for. The subject of that token is the principal, the actor remains the agent's own workload identity, the token is valid in one trust domain for one transaction, and the gateway verifies it rather than choosing the principal [@rfc8693]. The reputation database does not answer that question. Approval means only the approved work and only the approved class of data. A bonded agent is the special case of that fourth question: the approved work is a read.

**History and the monitor.** The Agent Reputation Database holds what this agent has done on this node, for a retention the administrator sets between hours and weeks. For a cold start, the fingerprint is the starting point of the first entry. The Recorder forwards the drift result it already computed for the work-order report to the workload host. That result compares the work to organizational policy and guidance and requires that the agent adhered to its system prompt. It does not judge whether the data produced are correct. A misidentification inside the system prompt, such as calling a dog a kangaroo and asserting it, adheres. Exfiltrating the source database leaves the system prompt, including when the user prompt asked for it. Staying inside both standards sets the entry as the base run. The baseline is accumulated over a series of runs whose length the administrator sets. The attestation gateway gives an approved workload's gathered facts to an Agent Monitoring Client. The client defines anomalous behavior as anything outside the baseline of previous work. Anomalous behavior, or an attempt to access a new resource, moves that validated workload into the sandbox.

**The sandbox.** If the profile or scope is not yet confirmed, or the behavior is not in the reputation database, the agent starts in the sandbox so the task need not hang while a new Bellman list is fetched. Writes and deletes are recorded as CRDT shards, which are local until a later reconcile [@shapiro2018]. For a recognized agent whose behavior changed, the gateway asks the dispatcher to validate the initiating workload prompt. After the profile and scope are validated, the shards reconcile into the primary database and the agent may retrieve approved outputs or execute follow-on tasks. Until that authorization, the only outward message is a keepalive.

**The Recorder and the next task.** The agent returns a structured report naming the information retrieved, the tools called, the resources accessed, and the queries made. The Recorder compares the result with organizational policy and guidance and with the system prompt, sanitizes restricted information, and runs the report through guardrails and company policy aimed at direct injection. A report that fails is rejected, and the Recorder tells the dispatcher to redo the workload. Reports that belong to one multi-turn workflow carry a session tag. Before one of them is added in sequence to memory, the chain is audited. The note names a simple classifier, of the kind it calls a JEV model, as the reader of that sequence. A chain read as dangerous is stopped. Its reports are isolated, quarantined, and flagged, and a person is alerted. They are not added to memory. The dispatcher then reattempts the task with a different minted agent, a more restrictive mint, or a different resource, and a failed report is the occasion for the bonded agents above. The comparison the Recorder already computed is forwarded to the workload host for the initial reputation entry, and it is not a second evaluation of the data. Only a result that stayed inside policy, adhered to the system prompt, passed the direct-injection check, and sits in a chain the audit did not quarantine enters the context memory graph and the Completed Work Order Report database, which are what the dispatcher reads. For a cold start with no previous history, that same result is what makes the run the base run. The agent's context, tool calling, tool cache, memory, and indices are then cleared, and the agent returns to the warm pool. A repeated task is briefed with the admitted report. An agent implicated in prompt injection is decommissioned.

**Subcontracts.** A helper is not spawned by the caller. It is minted and requested from a dispatcher. A local dispatcher cannot mint a helper that leaves the resource boundary. Helpers carry stricter limits than the primary agent. The central list records the helper so a later task can request that kind of help only when the scope is equal or reduced.

The orchestrator produces a granular plan from the user request and from the discovery memory, including the topology of the boundaries the task must cross. A policy-as-code engine, of the kind the note names asago, audits the plan against company policy and returns it with notes when the plan fails [@asago]. The orchestrator revises until the plan passes or the administrator's turn limit is reached. The initial user prompt, including the best-guess addendum on a new agent's first task, passes input guardrails before an agent runs it. The dispatcher assigns the passing plan by least privilege and writes the context brief. It prefers existing agents that each do one job over minting one agent that does many. When it must mint, it sets the grain along security boundaries, so a fetch at a vendor boundary is not the same profile as a write in the core. Least privilege is the requirement that the rights used now are the rights this job needs [@saltzer1975]. Zero trust adds that a grant for one resource is not a grant for the next [@nist800207]. Screening the untrusted prompt before it becomes the plan is the same separation of a quarantined input from a privileged planner [@willison2023].

## 3. The inferences

### 3.1 A matching check value means the formulation was not replaced

The check value is a function of the minted prompt and its creation metadata. The gateway recomputes that function on the prompt it sees. Equality holds only when the prompt is the minted prompt. Inequality means this process is not the agent the registry names.

This is an integrity inference, not an inference about the wisdom of the prompt. It is the same form as checking a published measurement of an artifact before trusting the artifact: the consumer does not take the producer's word in the moment [@intoto2019; @slsa12]. SPIRE still supplies the workload identity. The check value supplies the formulation bound to that identity. Neither one alone is the conjunction the gateway needs. A valid SVID with a swapped prompt fails the check value. A matching prompt on an unattested process fails SPIRE.

Indirect prompt injection and a coerced request do not have to edit the system prompt. They change data or the requested task [@greshake2023]. The check-value inference does not claim to detect those. It claims that the formulation against which they will be judged has not been quietly replaced. Later inferences do the judging.

The best-guess workflow is attached to the first user prompt of a newly minted agent, and the note excludes it from the system prompt. A synthesis of earlier workloads therefore cannot change the check value. The addendum is an input to the first sandboxed run. Whether that input stays inside the minted profile is a later inference, not part of this one.

### 3.2 Distinct profiles keep distinct duties apart

Separation of privilege says that if two conditions must both be met, and the means of meeting them are held apart, then one deception is not sufficient [@saltzer1975]. The supply-chain report crosses four trust boundaries. The dispatcher supplies the split: faced with several existing agents that each do one job, it uses those agents rather than mint one agent that can read the core, the vendor network, and the internet. A new mint stops at a security boundary. The inference holds when the gateway's fourth question refuses an action that belongs to another profile, so the agent that fetched the vendor page is not the agent that writes the core record.

Purpose-based access control is the same inference applied to data. An access is allowed when the purpose of the access complies with the purpose bound to the data, and a role name is not that purpose [@byun2005]. "Speaks for the administrator" does not entail "may read HR" or "may ask about the firewall." The profile is the purpose. The resource enforces it.

The database pair is the same inference at the level of an operation. The two tools are alike to authentication. They are unalike if they were minted as different profiles, one of which does not authorize bulk deletion of drafts. A prompt injection can change what the model attempts. It cannot change which profile the gateway will honor, because that profile is the checked prompt, not the injected text. Excessive agency is the failure mode in which the tool's permissions are wider than the job [@owasp2024excessive]. The note's inference is that the profile, enforced at the resource, is what keeps them from being wider.

### 3.3 Anything outside the baseline is contained

The note defines anomalous behavior as anything outside the baseline of previous work on that node. The definition is exhaustive: an action the baseline does not contain is outside it. A new query class, or a fetch agent attempting a firewall query or a remote HR read, is therefore anomalous whenever the reputation database does not already record that action.

The architecture has a place to put that result. A cold start has no previous work, so its first task runs in the sandbox and is the fingerprint. That task becomes the starting point of the reputation entry, and it becomes the base run when the result stayed inside organizational policy and adhered to the system prompt. The baseline itself is a series of such runs, of a length the administrator sets. A wrong answer inside the system prompt is part of that series. A first result that leaves the system prompt, such as an exfiltration of the source database, is withheld from the base run. Behavior still absent from the database starts in the sandbox. An already validated agent that departs from the baseline, or that attempts a new resource, is moved there by the monitoring client. History-based access control is the general form of this step. What has already happened can change what may happen next, whether by accumulating a prohibition, as in the Chinese Wall policy [@brewer1989], or by carrying the rights of code that has actually run [@abadi2003], or by updating a subject attribute that an ongoing check continues to read [@park2004]. The note's variant is local and comparative: the attribute is the baseline, and the ongoing check is the monitor.

The inference "unexpected behavior does not land in the primary store" follows if the monitor and the sandbox are on the path of the action. The sandbox records writes and deletes as shards and does not reconcile them until validation. Until then it emits only a keepalive, so the unexpected behavior also cannot be the channel that carries data out. Containment is then both integrity and confidentiality for the interval before validation.

### 3.4 Promotion re-applies the profile

Reconcile is not implied by "the agent was allowed to start." The note requires an updated registry and a validated profile and scope, and, for a behavioral change of a known agent, a dispatcher validation of the initiating workload prompt. The sound reading of that validation is a comparison: the prompt that started the work is accepted only if it falls inside the minted profile. The dispatcher already applied least privilege when it wrote the brief. The gateway's later question repeats the constraint at the resource, which is the point of not trusting the agent's own account of what it needs.

A cold start is the same separation of objects, stated by the note. The system prompt is what the check value binds. The first user prompt is a separate text, chosen from similar workloads or synthesized from several, and the first task that carries it is the fingerprint. Promotion validates the profile. The shards of that task inherit the validation only when they are the effects of a user prompt that itself falls inside the profile. Admission of the same task to the reputation base run is a further predicate. The forwarded drift result must say the work stayed inside organizational policy and adhered to the system prompt. The check value establishes that the system prompt is the minted one. Adherence establishes that the result stayed inside it. A user prompt that pulls the work off that prompt fails adherence. The predicate is independent of the shard reconcile, and it is independent of whether the data were correct.

Follow-on tasks after promotion are a new use. The five questions are per approval. A follow-on task that is a new dispatch is covered because it re-enters the dispatcher. A follow-on task that rides on the earlier yes is covered only if it stays inside the profile that was just validated. The architecture's own approval rule supplies that limit.

### 3.5 The next task receives only an admitted report

Clearing context, tool calling, tool cache, memory, and indices removes the agent's own residue. The continuity object is the report. The Recorder is the only writer of the stores the dispatcher reads, and it writes after four predicates: the result stayed inside organizational policy and adhered to the system prompt, restricted information has been removed, guardrails and company policy have accepted the report against direct injection, and the session chain was not quarantined. The first predicate is the drift result already computed for the report. A factual error inside the system prompt does not fail it. An action outside the system prompt does. A report that stays inside the system prompt and still carries an instruction from a page it was allowed to read fails the fourth predicate when the chain is read as dangerous. That report is quarantined. It is not the next brief.

From those predicates, non-propagation follows for any result that leaves the system prompt, and for any chain the audit stops. Exfiltrating the source database fails drift and is not admitted, whether the user prompt requested it or the brief called it guidance. The same failure withholds a cold-start run from the reputation base run. A report that carries restricted data fails sanitization. A direct injection in the report fails the guardrail, and the dispatcher is told to redo the workload. A dangerous chain is stopped before the next report is added to memory. The redo that has to go back to the nodes which produced the failure uses bonded agents. They are read-only, so the workaround cannot write the fault into the primary store. Their reports are checked for the same fault. A report that still shows it is kept for forensics and is never added to memory. If the task cannot be finished without that report, the workflow fails and the user is told. The next brief is drawn from the admitted stores, so a report that failed does not become instructions. The classifier's rate of success is not part of this inference. The inference is the withhold the note attaches to a dangerous reading. Decommissioning the agent forces a Bellman publication, so the other nodes receive the revocation without waiting for the next scheduled list. SPIRE issues a workload token only when the agent's remaining countdown is longer than that token's lifetime, and only when a publication that can reset the countdown comes before the countdown expires. An agent with fifteen minutes left, and a scheduled list thirty minutes away, receives no token. An agent with forty-five minutes left, and a list in thirty minutes that will reset the countdown, can receive one. The node that detected the injection can also refuse it immediately.

A result that stays inside the system prompt has the opposite consequence. A cold-start run that does, including one that misidentifies what it was asked to look at, becomes the base run, and further adhering runs accumulate into the baseline. The series records how this agent performs the duty in its system prompt. It does not record a departure from that prompt, and it does not certify the data. The user prompt and the brief can name the task. They cannot amend the system prompt the adherence check uses. A coerced use of the duty that prompt already contains still passes, because the result adhered.

This is why shared memory is a set of briefs rather than a channel. Agent-to-agent text can carry an instruction forward [@lee2024infection]. The inference does not deny that. It says the instruction reaches the next task only by passing the Recorder, and the wiped agent has no side channel of its own context left to carry it.

### 3.6 A helper cannot be a second copy of the caller

A subcontract creates another minted agent. Its restrictions are stricter than the caller's. It cannot be minted locally in a form that leaves the boundary. The caller's request names a need. The dispatcher mints the helper and the gateway applies the helper's own check value and profile.

The confused-deputy pattern is a caller that both names a target and borrows a privilege it does not hold [@hardy1988]. The inference blocks that pattern when the helper's profile is a subset of what the caller's profile allows for this task, and the gateway enforces the helper's profile rather than the caller's request. Stricter limits are that subset relation. Isolated helpers with a reduced set of actions are the same idea applied to untrusted data [@beurer2025patterns]. The note's reuse rule is the same relation stated as a condition: a remembered helper is requested again only for equal or reduced scope. A later task with a wider scope does not inherit the earlier helper.

### 3.7 What the wrapper adds to SPIFFE/SPIRE

SPIRE answers who the workload is and where it is running [@spiffe; @spire]. The wrapper answers the context questions a valid identity leaves open. The note's list lines up as follows.

- Who, and where: SPIRE, unchanged. The check value is added so the formulation published for that identity is the formulation presented.
- On whose behalf: a short-lived transaction token. The subject is the principal. The actor remains the agent's SPIRE identity. A gateway outside the token's trust domain refuses it. The token is not part of the check value [@rfc8693].
- How: the immutable system prompt. A direct prompt injection can ask the agent to ignore it. The check value fails if the prompt was replaced. Adherence fails if the result left it.
- What: the profile, reinforced by the baseline. An indirect prompt injection, brought back from a vendor site or the internet, can ask for a wider action. The profile is what the gateway will honor.
- The brief: context hacking. Shared memory is a series of admitted reports. A session chain read as dangerous is quarantined before the next report is added, and a bonded redo's failed report is never added. Discovery reports live in another memory. The agent's own context, tools, cache, memory, and indices are wiped. An instruction becomes the next task only by passing the Recorder.
- When: the Bellman list. A revocation forces a publication. Unused agents carry a countdown on that list, and a later list that still includes the agent resets the countdown. SPIRE withholds a token whose lifetime would run past the countdown, and it withholds a token when the countdown expires before the next publication can reset it. The reputation window, hours to weeks, is the local bound on how long previous behavior remains the baseline.

The claim that follows is confinement of those four attacks to the task that was minted. A wider sentence in the note, that no agent can execute an entire kill chain, is not required for the wrapper and is not the conclusion this paper defends.

### 3.8 The request and the plan are screened before an agent runs

Input guardrails apply to the initial user prompt. Output guardrails apply to the orchestrator's plan. A prompt that asks an agent to leave its duty, such as a request to exfiltrate the source database, fails before the orchestrator plans it. A plan that adds a second duty, or that turns the narrow delete into the bulk delete, fails before the dispatcher assigns it. The best-guess addendum is an initial user prompt, so a synthesis that imports another duty fails the same input check and does not become the fingerprint the sandbox runs.

The standard is the duty and organizational policy. A wrong identification inside that duty passes, as it does at the Recorder. A request that asks only for the duty the requester already holds also passes. The leader's request for a supply-chain report is that case. The guardrails see the request. They do not see the page the agent will read at the vendor boundary.

Indirect prompt injection arrives in that page, not in the initial user prompt and not in the plan [@greshake2023]. The front door is closed to a poisoned request and to a poisoned plan. The instruction carried home is a matter for the chain audit. A chain read as dangerous is quarantined before it is added to memory. The redo is read-only, and a bonded report that shows the same fault is kept for forensics. Discovery memory is neither of those stores.

## 4. Assumptions the inferences need

The inferences are valid given the architecture as stated, together with the following readings. They are the readings under which each component does the job the conclusion assigns it.

1. The dispatcher's grain rule is followed at mint time. The core, the intranet, a vendor network, and the internet are not one prompt. A new mint stops at a security boundary. The gateway then enforces the profile it was given. It does not re-cut a wide prompt.
2. The gateway and the resource decide the fourth question from the profile and the request. They do not decide it from the agent's statement of why it needs the data.
3. The best-guess addendum is the first user prompt and is excluded from the system prompt, which the note states. A synthesis of earlier workloads used as that prompt stays inside the minted profile. The shards produced under it are reconciled only when they fall inside that profile.
4. The monitoring client is on the path of actions. An out-of-baseline action, or an attempt to reach a new resource, is contained in the sandbox instead of being applied to the primary store and noticed afterward.
5. Dispatcher validation of the initiating prompt compares that prompt to the minted profile. It is not a re-confirmation that the dispatcher itself issued the prompt.
6. The shards reconciled after that check are the effects of the prompt that was checked. A later, different set of effects requires its own check.
7. The context memory graph and the report database become readable by the dispatcher only after drift, sanitization, the direct-injection check, and the chain audit have all passed. A quarantined chain is not readable as a brief. A bonded report that shows the fault which caused the redo is kept for forensics and is not added to either store.
8. "Equal or reduced scope" is decided by comparing minted profiles. A helper reused under that rule is not wider than the caller of the new task.
9. "When" is the countdown on the Bellman list. A revocation forces a publication. SPIRE issues a token only when the remaining countdown exceeds the token's lifetime and a resetting publication occurs before the countdown expires.
10. The drift result compares the work to organizational policy and guidance and requires adherence to the system prompt. A wrong answer inside the system prompt is a reasonable fault and passes. An action outside the system prompt, such as exfiltrating the source database, fails. The score forwarded to the workload host is that result, already computed for the work-order report.
11. Adherence is to the minted system prompt. The user prompt and the task brief do not amend it. A result that follows them off the system prompt fails drift and does not join the baseline series. The length of the series is an administrative parameter.
12. Input guardrails screen the initial user prompt, including the best-guess addendum, against organizational policy and the duty before an agent runs it. Output guardrails screen the orchestrator's plan against that same standard before the dispatcher assigns it. A prompt or a plan that leaves the duty fails. A prompt that stays inside the requester's duty passes. Data the agent later reads are outside both checks. The chain audit is the check on those later data once they have been filed as reports.
13. Bonded agents are used only after a failed report. The check value hashes the whole prompt, including the delegated prompt, and a synchronous publication reaches only the nodes that produced the failure, before dispatch. Each bonded agent is read-only, does one part, returns only to the Recorder, and is removed when its report is in. A workflow that cannot avoid the isolated fault fails.

None of these is an experimental result. Each is a condition on how the components are connected. Where the note already connects them, the condition is a reading of that connection. Where it does not, the companion paper treats the conclusion as not yet entailed [@critique].

## 5. Conclusion

The note's conclusion follows when formulation, profile, history, containment, and admission are a single chain. The check value fixes the formulation. A best-guess workflow is the first user prompt and does not enter that formulation. The dispatcher cuts profiles along security boundaries and prefers agents that already have a single job. The baseline marks anything else as anomalous. A cold start's first task is the fingerprint. The drift result already computed for the report is forwarded to the workload host. The run becomes the reputation base run when the work stayed inside organizational policy and adhered to the system prompt, and the baseline is a series of such runs. A wrong answer inside the system prompt can be in that series. An exfiltration cannot. One requested in the initial user prompt fails the input guardrail before an agent runs, and one that appears later fails adherence. The sandbox holds that work without exfiltration until the profile, and for a changed behavior the initiating prompt, are validated. The Recorder is the only way a finished task becomes the next task's brief. A chain read as dangerous is quarantined before that brief is written. The workaround is a bonded, read-only, one-shot pass, and a report that still shows the fault is kept for forensics and is never briefed. A workflow that cannot continue without it fails. The agent's context, tools, cache, memory, and indices do not survive to compete with that brief. A helper comes back only for an equal or narrower scope.

That chain is the wrapper. SPIFFE/SPIRE still names the workload and the node. The wrapper keeps a direct injection from replacing the system prompt, an indirect injection from becoming the next brief or the discovery context, a hacked context from outliving the task that produced it, and a commission or a memory from being used after its time. It is a theoretical argument. Its open questions are missing connections between components, not missing measurements. Those connections are the subject of the companion papers.
